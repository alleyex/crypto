# 2026-03-29 修改紀錄

## Closed Trades 混用 1m / 5m 配對修補

### 問題背景

遠端 scheduler 已切換為：

- `runtime/scheduler.timeframes = 5m`
- `runtime/scheduler.strategy = ppo`

但 Admin UI 的 closed trades 仍出現像是只持有 `1.02 min` 的短單，看起來像 `5m` 模型在 1 分鐘內平倉。

範例：

- `Entry = 66748.24`
- `Exit = 66756.82`
- `Closed At = 2026-03-28 14:58:40`
- `Hold = 1.02 min`

### 根因

這筆其實是舊的 `1m` 交易，不是新的 `5m` 交易。

原本 `/strategies/closed-trades` 的配對邏輯在 `app/query/read_service.py` 只用：

- `strategy_name`
- `symbol`

當作倉位 key，沒有把 `timeframe` 納入。

因此在切換到 `5m` 之後，新的 `5m SELL` 可能會去配對先前未平掉的 `1m BUY`，造成：

- `1m` / `5m` closed trade 被混成同一筆
- UI 看起來像 `5m` 單只持有 1 分鐘

### 修補內容

#### `app/query/read_service.py`

將 closed trade 配對 key 從：

- `(strategy_name, symbol)`

改為：

- `(strategy_name, symbol, timeframe)`

同步修正：

- `get_strategy_closed_trades()`
- execution report / closed trade 統計內部的 entry lookup

現在 BUY / SELL 只會在相同 timeframe 下互相配對。

#### `app/admin/page.py`

Closed trades 卡片標題改為直接顯示：

- `strategy_name · symbol/timeframe`

例如：

- `ppo · BTCUSDT/5m`
- `ppo · BTCUSDT/1m`

避免 UI 誤導。

### 遠端驗證

已同步修補到：

- `root@168.144.35.241:/root/crypto`

並重啟 API 後重新驗證 `/strategies/closed-trades?limit=12`。

修補後結果：

- 最新 closed trades 前 4 筆正確顯示為 `5m`
- 後續舊紀錄才是 `1m`

範例：

- `2026-03-28 23:00:08` → `BTCUSDT`, `5m`
- `2026-03-28 22:40:51` → `BTCUSDT`, `5m`
- `2026-03-28 21:20:42` → `BTCUSDT`, `5m`
- `2026-03-28 20:35:03` → `BTCUSDT`, `5m`
- `2026-03-28 15:21:01` → `BTCUSDT`, `1m`
- `2026-03-28 14:58:40` → `BTCUSDT`, `1m`

這證明：

- `5m` 交易並沒有被 1 分鐘平倉
- 問題來自 closed trades API 的跨 timeframe 混配
- 修補後 `1m` / `5m` 已正確分開

### 補充觀察

遠端實際成交資料顯示：

- 最新 `5m` orders 為 `446` 到 `455`

## RL Env Reward Leakage 修正

### 問題

`app/rl/crypto_env.py` 的 `step()` 使用 `new_position × log_ret_1[t]` 計算 reward，等同於讓 agent 在看到 `log_ret_1[t]` 的同時用同一根 bar 的報酬獲利，屬於 look-ahead leakage。

這是 Job #43–45 edge 高達 +0.19 的根本原因（win rate=1.0、trades 150+ 次/window，明顯異常）。

### 修正

```python
# 修正前（leakage）
step_pnl = self._position * log_ret   # ← new_position

# 修正後
old_position = self._position
new_position = _ACTION_TO_POS[int(action)]
...
step_pnl = old_position * log_ret     # ← position held ENTERING bar t
reward   = step_pnl - fee
```

修正後 edge 從 +0.19 降至 +0.01 左右（MARGINAL），trades 降至 5–25 次/window，行為正常。

## 特徵集升級 V2 → V3（33 features）

### 背景

V2 25 個特徵的 LGBM baseline accuracy 為 0.5135，Null Importance 測試顯示只有 5 個特徵統計上超過噪音基準（`adx_14`、`upper_wick_ratio`、`log_ret_3`、`lower_wick_ratio`、`macd_hist_norm`），其餘皆在隨機水準。

### 新增特徵（8 個）

| 特徵 | 類型 | 說明 |
|------|------|------|
| `bb_pct` | Type ① | Bollinger Band 位置 [0,1] |
| `bb_width_norm` | Type ① | BB 寬度 / close |
| `dist_vwap_20` | Type ① | 20 期滾動 VWAP 距離 |
| `adx_14` | Type ① | ADX 趨勢強度 [0,1] |
| `flow_imbalance_5` | Type ① | 5 期累積 taker flow imbalance |
| `flow_imbalance_20` | Type ① | 20 期累積 taker flow imbalance |
| `streak` | Type ① | 連續漲跌 bar 數 / 10，clip[-1,1] |
| `macd_hist_norm` | Type ③ | MACD histogram / close |

### V3 LGBM 結果

V3（33 features）的 accuracy 反而從 0.5135 降至 0.5062，新特徵整體引入噪音而非信號。Null Importance 確認信號極弱，根本問題是 5m BTCUSDT 可預測性低，而非特徵種類不足。

## LGBM Walk-Forward 修正

### 問題

`scripts/run_lgbm_walkforward.py` 的 Sharpe 計算有兩個錯誤：

1. `actual_ret` 使用 `log_ret_1`（當根 bar 報酬），應改為 `fwd_log_ret_1`（下一根 bar 報酬）
2. `periods_per_year=525_600`（1m 因子）用於 5m 資料，Sharpe 被放大 √5 ≈ 2.24 倍

### 修正

```python
df["fwd_log_ret_1"] = df["log_ret_1"].shift(-1)
df = df.dropna(subset=feat_cols + ["fwd_log_ret_1"]).reset_index(drop=True)
df["target"] = (df["fwd_log_ret_1"] > 0).astype(int)
...
actual_ret = df["fwd_log_ret_1"].iloc[train_end:test_end].values
```

修正後 5m LGBM Sharpe 從表面上的 +6.9 降至實際約 +3.1。

## Order Book Snapshot Collector

### 背景

LGBM Null Importance 分析顯示現有特徵信號極弱，最有潛力的補強方向是 Binance L2 order book 的 bid-ask imbalance。由於 Binance 不提供歷史 order book，需從現在開始收集。

### 實作

每分鐘收集一次 Binance top-10 depth，對齊現有 1m candle 時間戳。

**新增檔案：**

- `app/data/orderbook_service.py` — fetch / save / stats；預設開啟，pause file 控制
- `app/pipeline/orderbook_job.py` — scheduler job，每分鐘執行

**修改檔案：**

- `app/core/migrations.py` — migration 041：建立 `order_book_snapshots` table
- `app/scheduler/runner.py` — loop 加入 `run_orderbook_job()`，error 靜默不影響主流程
- `app/api/main.py` — 新增 `GET /orderbook/status`、`POST /orderbook/enable`、`POST /orderbook/pause`
- `app/admin/page.py` — Market Data 分頁加入 Order Book Collection 區塊

**控制邏輯：**

預設啟動即收集（無需手動 enable）。按 Pause 寫入 `runtime/orderbook.paused`；重啟後若無 pause 檔案則自動恢復。

**儲存量估算：** 約 150 MB/年（top-10 × 2 side + 預算指標）

## 超參數搜索總結（5m，env leakage 修正後）

固定環境修正後的最佳結果：

| 配置 | Avg Edge | Verdict |
|------|----------|---------|
| gamma=0.85, 25 feat (#52-53) | +0.001~+0.016 | MARGINAL |
| gamma=0.99, fs=1, 1M (#60) | +0.0075 | FAIL |
| gamma=0.99, 2M (#69) | −0.0042 | FAIL（beats 5/8）|

**調參結論：**
- frame_stack 增大 → trades 暴增 → edge 惡化（1→4→8→16 呈線性）
- ent_coef 增大 → trades 增多 → edge 惡化
- gamma=0.99 是目前最佳，但信號不穩定

**根本瓶頸：**
- fee=0.1%/side 過高，5m K 棒平均移動不足以覆蓋成本
- LGBM accuracy 只有 0.51，特徵集信號本身極弱
